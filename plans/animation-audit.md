# Animation audit

Stamped at `6ec4bab`. Resolves [#10](https://github.com/wmbryce/pixel-fortune/issues/10).

**Re-stamped at `7ba0160`.** The findings table below is the audit as it was found at `6ec4bab` and is left as written — the `file:line` references point at code that has since moved. What became of each finding is the **Status** column and the [Re-stamp](#re-stamp) section; read those before believing a row. Three findings were _superseded_ rather than applied: the fix that landed is not the fix recommended here, and the reasoning is why the current code looks the way it does.

Audited against the eight categories in the `improve-animations` playbook (Emil Kowalski's motion philosophy). Every finding below was re-read at its `file:line` before being listed.

## Recon

|                 |                                                                               |
| --------------- | ----------------------------------------------------------------------------- |
| Stack           | Next 16 App Router, React 19, `motion` 12 (`motion/react`), Tailwind 3        |
| Motion surfaces | `Card.tsx`, `CardTable.tsx`, `DialogBox/index.tsx`, plus 4 Tailwind keyframes |
| Tokens          | **None.** Every duration, curve and offset is hand-typed inline               |
| Personality     | Playful pixel-art RPG — earns a larger delight budget than a dashboard        |

**Frequency map.** This is a short-session app with one flow: land → deal 5 cards → reveal each → read the fortune → reset. Nothing is hit 100+ times/day, so almost nothing here should be _deleted_ for being over-animated. That inverts the usual audit result — the dominant problem is motion that is **wrong or missing**, not motion that is excessive.

**On spring `duration` (#3, #8, #9, #10).** A `motion` 12 spring does _not_ discard `duration`. `getSpringOptions` treats it as a `durationKeys` member and routes to `findSpring` (`motion-dom/dist/cjs/index.js:872-895`); seconds→ms conversion at `:3299`. Measured against the installed `motion` 12.43.0:

```
spring duration:1000ms  -> settles at 1000 ms
spring duration:2000ms  -> settles at 2000 ms
spring (no duration)    -> settles at 1068 ms
spring 1000ms+bounce0.2 -> settles at 1000 ms
```

`bounce`/`visualDuration` shape the curve, they do not enable `duration`. Both values are live — and so is every other spring `duration` in the app. All seven live sites:

| --------------------------------------------------------- | --------------- | ----------- | ------------- |
| `Card.tsx:89`                                             | `duration: 1`   | 1000ms      | #8            |
| `DialogBox/index.tsx:227`                                 | `duration: 2`   | 2000ms      | #9            |
| `DialogBox/index.tsx:171` (`y`, loading)                  | `duration: 1`   | 1000ms      | #3            |
| `DialogBox/index.tsx:181` (`height`, visible)             | `duration: 1`   | 1000ms      | #3            |

Seven, not two — no spring `duration` in this codebase is inert. Six are over the 300ms budget; only `transit` is under it.

## Missed opportunities

Additive, not corrective. Four real seams observed in the flow:

1. **`/welcome` → `/tarot` is a hard swap.** `router.push` with nothing connecting the two screens; the 3s page fade (#7) is a blunt substitute for a real transition. The most spatially meaningful moment in the app has no motion explaining it. — **Done** (#29). `PageTransition` holds `router.push` until the exit has played; `loading.tsx` under each route covers the fetch.
2. **The fortune's arrival is unmarked.** The mutation resolves and text simply begins typing. No transition between "the spirits are consulting" and "here is your reading" — the emotional peak of the app lands flat. — **Partly.** #37 gives it the `arrive` cue, the one sound no hand causes, and #34 announces it to a screen reader. Visually it is still unmarked: the reveal prompt is on a fixed 2200ms beat and a reading arriving is deliberately not a move in the machine (#30), so any motion here has to come from the beat, not from the arrival. **Open.**
3. **Blocked-continue has no physical feedback.** Clicking Continue before all cards are revealed sets `errorText` and nothing moves. A short shake on the dialog, or a pulse on the unrevealed cards, would say it without prose. — **Done** (#29 `SHAKE`, #34 the keyed `role="alert"` beside it).
4. **Reset teleports.** "Complete" calls `router.push('/welcome')` — the same hard swap as #1, at the moment the loop closes. — **Done**, with #1.

## Suggested execution order

Finding #9 is a one-line change that removes a 2s wait on the app's main button — take it first. Findings #2, #11, #13 are pure deletions and can land immediately — they shrink the surface everything else has to work against. #1 and #4 are the two that change how the app _feels_ and deserve the most care. #5 and #12 are best done once, late, across everything.

Nothing here is blocked on the reveal-interaction prototype ([#13](https://github.com/wmbryce/pixel-fortune/issues/13)) except #1, which that prototype exists to settle.

_Followed, near enough: #9 went first, #1 landed via the prototype (#27), and #5/#12 landed together and late (#29). See the re-stamp below for where each ended up._

## Re-stamp

At `7ba0160`. Every finding below was re-read against the code before its status was written; the statuses are in the **Status** column above.

**Done, as recommended.** #1 (the flip, [#13](https://github.com/wmbryce/pixel-fortune/issues/13) → #27 — landed critically damped at `bounce: 0` rather than the `0.2` suggested here, because a tap carries no momentum for a bounce to express), #2, #5 (`useReducedMotionPref()`, read by five surfaces; a blanket disable is what `test/reduced-motion.test.tsx` exists to catch), #6 (`useHoverCapable` plus a `whileTap`), #7 (the 3s `animate-fadeIn` is gone; the entrance is CSS in `_components/page-transition.css` at `DURATION.page` = 240ms with `EASE_OUT`), #8 (subsumed by #1, as predicted), #9 (`SPRING.snap`, 400ms), #11 (all four removed; the one surviving `AnimatePresence` wraps the button row, which does come and go), #12 (`src/app/_libs/motion.ts` — no duration or spring is hand-typed at a call site any more), #14 (moved out of Tailwind into `welcome/welcome.css` as `hint-blink`, gated on `prefers-reduced-motion` and on the app-level override).

**Superseded.**

- **#3 — `height` stayed, and that is now the decision.** The 1000ms is gone (`SPRING.settle`, 450ms), but `scaleY` was rejected in #16: the 8px pixel border and the typewriter's scroll box both distort under a scale. The layout cost the finding worried about is paid for instead — `tarot/page.tsx` reserves the strip at `h-[292px]` from the first frame, so the box growing inside it costs nothing else on the page.
- **#4 — the stagger is still a `setTimeout` chain, on purpose.** `staggerChildren` cannot express what the deal became in #14: cards mount progressively (`slice(0, dealt)`) and travel through two stages, fan then grid, on `DEAL_MS` = 260ms with a `SETTLE_DELAY_MS` beat after the last. The effect now cancels on cleanup and the reset is adjusted during render, so the lint error is gone and a new hand cannot be dealt on top of the last one's progress.
- **#10 — the travel is measured, not a percentage.** `y: -box.h`, off the top of the stage `CardTable` has actually measured, rather than the `-120%` of the card's own height suggested here. Same problem, better answer: the spread is measured throughout (#14/#28), so the deal is measured with it.

**Open.**

- **#13, in part.** The deletions landed, and more besides — `staggerDelay`, `bg-grey` and the `animate-*` usages are all gone. Two remnants: `TypingText.tsx:119` still carries `font-pixel`, which names no `fontFamily` key (`tailwind.config.ts` defines `sans`/`normal`), so the app's main reading surface still renders in the browser default rather than Pixelify — the `font-pixel` → `font-sans` fix is the one part of #13 that was never a deletion, and it is still not done. And `tailwind.config.ts:24-43` still declares the `fadeInOut` / `typing` / `blinking` keyframes and the `fade` / `fadeIn` / `type` / `blink` animations, none of which any file references now that #29 moved the entrance to CSS and #34 moved the blink to `welcome.css`. Both are behaviour-visible changes, so neither was taken as part of this re-stamp.
